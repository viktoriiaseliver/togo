# Togo — дневник собаки на iOS

Когда выводили, когда кормили, каким был стул. Общий дневник на семью
через CloudKit, виджеты, Live Activity, медицинский слой.

Общее на четыре проекта — `~/Projects/CLAUDE.md`. Здесь только своё.
Разбор любого правила — скилл `/метод`. Правила про токены,
локализацию, сторожей и стенд приезжают **сами**, когда откроешь
подходящий файл.

**Порядок чтения:** `git log` → верх `СТАТУС.md` → последняя запись
`docs/journal/` → работа → журнал (`make journal`), верх `СТАТУС.md`,
коммит.

## Нулевой шаг, которого нет у других проектов

```bash
source Gamut/.env.asc && python3 ~/Projects/отзывы.py Togo
```

**Единственный вход, которого git не знает по устройству:** отзывы
пишут снаружи, и никто не кладёт их в репозиторий. Кадры приходят
вместе с ними — `~/Projects/.отзывы/Togo/`.

Цена простоя измерена дважды: 07.10 отзывы не читал никто девять
дней, и в них лежал живой дефект розданной сборки; 09.10 оказалось,
что три её жалобы совпали с нашими починками — 15 часов, 22 минуты
и **две минуты** разрыва, то есть мы чинили то же место по другому
поводу, а отзыв не читал никто.

> **Отзыв, который никто не прочитал, — это не обратная связь,
> а её видимость.**

**Симулятор именем не прибит**: `DESTINATION` в `Makefile:12` берёт
UDID у `Tools/ci_simulator.py` в момент прогона. `TOGO_SIM=<сессия>`
даёт своё устройство `Togo-<сессия>` — **заводится само, если нет**.
Поэтому удалять `Togo-*` безопасно: скрипт пересоздаст.

**Потолок среды — 26.5** (`ci_simulator.py`, с 14.10). Выше него
не выбираем и не заводим: на iOS 27.0 стенд отказывает, и два прогона
на этом потеряны. Потолком меряется и **готовое** устройство, а не
только новое, — заведённое на 27.0 правку файла переживает, а по UDID
в логе от здорового не отличается ничем. Мерить новую среду нарочно —
`TOGO_RUNTIME_ANY=1`, отмена печатается в stderr. Поднимать потолок
рукой и с замером рядом, как номер сборки: это решение, а не
производная от того, что оказалось установлено.

## «Собирается ли» спрашивают БЕЗ стенда — и это снимает половину очереди

Две с половиной минуты, 205 файлов, ноль нагрузки на симулятор.
Половина заявок на слот 14.10 была ровно про этот вопрос.

```bash
git worktree add /tmp/togo-<сессия> <коммит>   # мерить КОММИТ, не дерево
cd /tmp/togo-<сессия>
SDK=$(xcrun --sdk iphonesimulator --show-sdk-path)
xcrun swiftc -typecheck -sdk "$SDK" -target arm64-apple-ios17.0-simulator \
  -swift-version 6 -default-isolation MainActor \
  -F "$SDK/../../Library/Frameworks" \
  $(find Togo TogoShared -name "*.swift") > /tmp/tc-<сессия>.log 2>&1
echo "МОЙ_RC=$?" >> /tmp/tc-<сессия>.log      # ПОСЛЕ команды, не через |
grep -ac "error:" /tmp/tc-<сессия>.log         # -a ОБЯЗАТЕЛЕН, см. ниже
grep -ac "modified during" /tmp/tc-<сессия>.log
```

**СПИСОК ОШИБОК — ПРО ОДИН ФАЙЛ ЗА ЗАХОД, а не про все. Замер
03.11.2026.** Сломал нарочно ДВА файла (`AppState.swift`
и `TodayScreen.swift`, по одной строке `let x: Int = "строка"`):

```
оба сломаны          rc=1 · 2 error: · назван ТОЛЬКО AppState.swift
починил первый       rc=1 · 2 error: · назван ТОЛЬКО TodayScreen.swift
```

> **Ноль и код возврата при этом ЧЕСТНЫЕ** — ложного зелёного здесь
> нет: пока сломан хоть один файл, `rc=1`, а `0 error:` выходит
> только когда чисто. Врёт не исход, а **объём работы**: «осталось
> починить две строки» читается из списка, которого хватает на одну.

Значит чинить по списку — **циклом до нуля**, а не одним заходом.
Записано по улике сессии, которая меняла 52 места: её первый заход
дал «4 error:» на двух классах поломок из трёх, лог был 25 строк,
и в нём не упоминались два файла с заведомой поломкой. Замер
не состоялся, а выглядел законченным.

**`grep` без `-a` на этом логе даёт МОЛЧАЛИВЫЙ ЛОЖНЫЙ ЗЕЛЁНЫЙ, и это
замер 26.10.2026, а не осторожность.** Прежняя редакция рецепта
кончалась `… 2>&1 | grep -E "error:|modified during"`. Предмет —
настоящий лог с **шестью** вхождениями `error:`:

```
file(1) про лог                              «data», не text
А. как было в рецепте, через конвейер        0 строк,  rc=0   ← ЛОЖНЫЙ ЗЕЛЁНЫЙ
Б. grep -c по файлу, без -a                  ПУСТО,    rc=1
В. grep -ac по файлу                         6,        rc=0   ← правда
Г. КОНТРОЛЬ: тот же запрос по UTF-8-логу     4,        rc=0
```

Механизм: `grep` здесь — `ugrep`, и лог, в котором ему попался
недопустимый байт, он считает двоичным. Тогда `-c` печатает **не ноль,
а ничего**, и возвращает `rc=1` — а `rc=1` у grep штатно значит
«не найдено». У формы нет ни одного признака отказа: ни числа,
ни кода. Через конвейер (форма А) выходит ровно «0 ошибок, успех».

> **Один и тот же `swiftc` даёт то текстовый лог, то двоичный** —
> контроль Г прошёл на логе предыдущего замера той же командой. Значит
> это наш класс «условие, привязанное к инструменту, меняет знак»:
> признак верен, пока в выводе не попался нужный байт, и переворачивается
> молча. Предсказать, какой лог окажется двоичным, нельзя — поэтому
> `-a` ставится ВСЕГДА, а не «когда лог похож на двоичный».

И второе из той же строки: **код возврата пишется в файл отдельной
командой, а не берётся из конвейера.** Через `|` он приезжает
от `grep`, то есть говорит «нашёл ли grep», а не «собралось ли».
Поймано на себе в том же замере: уведомление фоновой задачи сказало
«exit code 0», а файл в ту же секунду — `rc=1` и четыре `error:`.

**`-default-isolation MainActor` в этой строке — не украшение.** Без
него рецепт врёт в ОБЕ стороны, и замер каждой сто́ил проекту захода:
ложный зелёный 22.10, ложный красный 26.10. Разбор — третья граница
ниже.

**Worktree обязателен, и вот почему.** Запуск по общему дереву при
многих сессиях вернул:

```
error: input file 'Togo/App/AppState.swift' was modified during the build
exit code 0
```

Сосед правил файл, пока шёл замер. Замер **не состоялся** — а код
возврата ноль и строк `error:` в коде продукта ноль, то есть по обоим
признакам, на которые смотрят, это «ошибок нет».

> **Отказ пришёл в форме успеха.** `-typecheck` по живому дереву
> отвечает не «собирается ли коммит», а «мне не дали дочитать»,
> и говорит это нулём. Строку `modified during the build` читать
> наравне с `error:`.

И граница: это отвечает на «не положу ли красное всем», **не** на
«проходит ли тест». `swiftc -parse` не отвечает и на первое — он про
синтаксис; тот же файл дал «чисто» от парсера и десять ошибок
от SourceKit, и **оба ответа про инструмент, а не про код**.

**ВТОРАЯ ГРАНИЦА ОТМЕНЕНА ЗАМЕРОМ 26.10.2026: она стояла
на СЛОМАННОЙ КОМАНДЕ, а не на свойстве инструмента.** Здесь было
«рецепт НЕ БЕРЁТ ТЕСТ-ТАРГЕТЫ: `XCTest` находится, `XCTAssertTrue` —
„cannot find in scope", пятьдесят ошибок одного вида». Берёт.

```

правильный       $SDK/../../Library/Frameworks            есть, и в нём
                                                          XCTest.framework
контроль         test -d "$SDK" → есть (инструмент работает)
```

`$SDK/../..` — это **уже** `…/iPhoneSimulator.platform/Developer`,
то есть `Developer` в пути удваивается, и `-F` был мёртвым флагом
во всех прогонах. Вторая половина — своя: Swift-оверлей `XCTest`
лежит не во фреймворке, а в `<платформа>/usr/lib/XCTest.swiftmodule`,
и без `-I` на него не выходит ни один `-F`.

xcrun swiftc -typecheck -sdk "$SDK" -target arm64-apple-ios18.0-simulator \

  -F "$PLAT/Library/Frameworks" -I "$PLAT/usr/lib" <файлы теста>
```

```
предмет (TogoUITests/ПрокруткаПодПанелью.swift)   0 error:, rc=0
то же без -default-isolation MainActor            0 error:, rc=0

> **Отказ назвал сторону, которая отказала, а причину ему приписали.**

> восемь дней стояла в перечне оплаченных.

с путём из рецепта выходит `no such module 'XCTest'` — другое

**На сломанном пути стояли не только выводы, но и ВСЕ сегодняшние

### `-only-testing:TogoTests` не спасает от поломки в UI-таргете

`xcodebuild` собирает **всю схему**. Значит модульный прогон умирает
на сломанном UI-таргете, **не дойдя ни до одного теста**.

```
TogoUITests/ГостьНеПишет.swift:289
error: sending 'предикат' risks causing data races
** TEST FAILED **        ← у того, кто гнал -only-testing:TogoTests
```

> **Отказ приходит в той же форме, что собственный дефект**, и
> разбирается как свой. 14.10 сосед потратил прогон и полчаса,
> прежде чем посмотрел, **чей файл** в ошибке.

Различитель — одна команда: `git log -S '<строка из ошибки>' -- <файл>`
назовёт коммит, который её ввёл, и дальше видно, свой он или чужой.
Делать это **прежде** разбора, а не после.

> **У различителя есть слепое место, и оно шире самого различителя.**
> `-S` находит того, кто **ввёл строку**, а строка из сообщения
> о сборке называет **пострадавшего, не виновного**.
>
> ```
> ГостьНеПишет.swift:289  data race   строка и поломка родились вместе
>                                     → -S назвал виновника, совпало
> SeedData.swift:381  switch must be exhaustive
>                                     → -S назвал бы ПОСТРАДАВШЕГО;
>                                     виноват добавивший случай
>                                     в перечисление В ДРУГОМ ФАЙЛЕ
> ```
>
> Значит: **`-S` по строке из ошибки находит виновника только тогда,
> когда он и пострадавший — один файл.** Иначе искать надо по тому,
> что правка **ввела** (новый случай перечисления, новый параметр,
> новое требование к соседям), а это видно уже не из ошибки,
> а из дифа между здоровым и больным коммитом.
>
> Оба случая были 14.10 у одной сессии, и на первом она потеряла
> прогон именно потому, что ошибка указывала не на виновника.

Кадры: **38 файлов** пишут в `build/кадры-*` через `#filePath`
(замер 28.10.2026; прежняя редакция говорила «девять» и была неверна
вчетверо). `build/` в `.gitignore` — **то, что нужно сохранить,
выносить в `Дизайн/кадры-приёмки/` и коммитить.** 12.10 оттуда
спасено 116 кадров, лежавших нигде.

С 28.10 выносит и сам стенд: `вынестиКадры(из:набор:)`
(`TogoUITests/UITestHelpers.swift:180`) копирует снятое
в `Дизайн/кадры-приёмки/_последний-прогон/<набор>/` — вне
`.gitignore`, чтобы о кадрах говорил `git status`, а не память
того, кто их снял. Сам `_последний-прогон/` не коммитят.

**Каждый тест, пишущий кадры, обязан печатать счёт** — всегда,
в том числе после падения. В `TogoUITests` место счёта — `tearDown`,

```

Причина: «снято шесть» и «упал на третьем, снято два» выглядят

**а её отсутствия никто не ищет**. 14.10 в описи чуть не слиплись

строка итога говорит `passed`. Частая причина — форма базы в App Group
симулятора, лечится `xcrun simctl erase`.

> отказ стенда     URL: App Group симулятора
> ```
> Временную папку заводят сами тесты, поэтому подделать её отказ

## Красные линии

- **Продуктовые цвета литералом в HC не попадают** — только через
  `var(--ядро)`. Проверка: `python3 Tools/contrast_graphite.py`
  (124 пары, 8 непрохождений — текущее состояние).
- **Безымянная запись наружу не уезжает.** Два запрета в разных
  слоях: обмен не кладёт её в исходящий круг, миграция не трогает
  записи, которых человек не видел. Второй не ради экономии — иначе
  первому пришлось бы держать поток в одиночку.
- **Поле с обязательством показа вводить раньше показа нельзя.**
  `labMark` показывается только вместе с нашим вердиктом и подписью
  «кто сказал»; `method` требует правила «два значения разными
  методами нельзя рисовать одной линией», и **правила этого нет
  в графике, который уже есть** (`grep -rn "\.method = "`).
- **Не подставлять там, где подстановка станет утверждением
  человека.** Время забора, вес у рецепта, норма с бланка, предел
  прибора — пустые намеренно. Подсказку человек подтверждает,
  подстановку — нет, а запись потом читает врач.
- **Округление до одного знака — только для веса.** `16,75 нмоль/л`
  как `16,8` — потеря данных. Запрет на файл плюс проверка, что
  оставленное исключение ещё верно.
- **`ViewThatFits` запрещён**: держал в дереве обе раскладки,
  и озвучка находила две кнопки «Отменить».

## ▸ Менеджеру

Первое действие — отзывы (выше), затем `python3 ~/Projects/обход.py`
и `python3 ~/Projects/готовность.py`.

Чему в этом проекте нельзя верить:

- **`docs/APP-STORE.md`** сверялся с ASC 21.09 и стареет каждый день.
- **Статус `INVITED` в ASC** отвечает про один вход из двух:
  публичная ссылка имени не отдаёт. Из `INVITED` трижды выводили
  «сборку не ставила ни разу» — не следует.
- **Залито ≠ роздано ≠ привязано к версии.** Три отдельных ворот,
  и ни один код ответа исхода не предсказывает. Приёмка раздачи —
  `externalBuildState`; привязки — сверка привязанной сборки
  с новейшей, **обе величины печатать рядом**.
- **Верх `СТАТУС.md` может лежать только в рабочем дереве.**
  Различает `git show <коммит>:СТАТУС.md`, и его не делает никто.

Наряд называет коммит, на котором составлен. **Проверять наряд
в коде ПОКАЗА прежде, чем отдавать**: «десять записей в базе» — факт,
«человек видит десять строк» — вывод, и свёртка могла уже стоять.

## ▸ Разработке

Прежде первой строки — **прочитать голову модуля**: зелёный тест без
места вызова значит три разные вещи (нет причины — долг; причина
про ЧТО — решение; причина про КАК — долг с заданной формой),
и четвёртое место, где причина лежит, — **тест модуля**.

Порядок замера: сверить диф → `git commit -m "…" -- <пути>` →
`git worktree add /tmp/<имя> <коммит>` → прогон там, своя
`DerivedData` с PID. **Коммит ДО замера.** При закрытом слоте выбор
называть вслух: «кладу непроверенное» или «держу у себя».

Изоляция по умолчанию: у приложения `MainActor`, **у расширения
`TogoWidgetsExtension` нет**. Один файл в двух таргетах даёт красное
только в расширении. `@MainActor` на место вызова чинит приложение
и оставляет расширение красным; `nonisolated` у свойства снимает
требование у обоих — но проверить предмет, а не переносить правило.

Чего не делать без спроса: менять форму схемы (`SchemaVersions`),
снимать изоляцию у типа, читающего `@Model`, трогать чужое
незакоммиченное.

## ▸ Тестированию

Приёмка по сценариям, а не по частям. Красное имя разводить по трём
корзинам **до** записи в эталон:

```
A  ЗАКРЫТО ПОЧИНКОЙ    коммит СТАРШЕ починки — git merge-base
B  РЕШЕНИЕ С ХОЗЯИНОМ  есть что держит и кто хозяин → в эталон
C  РЕГРЕССИЯ           ни в эталоне, ни среди живых сессий → в работу
```

Отсутствие хозяина значит «не спросили», а не «нет».

**Сторож бывает настоящий, красный и немой** — когда прогон до него
не дошёл. Пока прогон умирает на тридцатом тесте из восьмисот,
семьсот семьдесят сторожей молчат, и молчание неотличимо от согласия.
После первого годного прогона эталон перечитывается **целиком**.

Поверхности, которых нельзя пройти прогоном, собирают дефекты:
под `-UITesting` всегда показывается главный экран, то есть
**онбординг с этим флагом не рисуется** — `AppRoot.body`,
`TogoApp.swift:243` на 14.10. Проверка за минуту:
`grep -n "isUITesting || settings.onboardingCompleted" Togo/App/TogoApp.swift`.

> **«В тестах никогда» — это пересказ, и он неверен.** Утверждение
> про ОДИН аргумент запуска. Входов **два**, и они отвечают на разные
> вопросы (замер 21.10.2026, решение Виктории о переводе):
>
> ```
> без -UITesting, стёртое устройство     что увидит ЧЕЛОВЕК на первом
>                                        запуске. Пишет в базу
> -UITesting -Сценарий onboarding        что нарисует КОД по просьбе.
>            -Онбординг                  пишемВБазу ЛОЖНО — не пишет
> ```
>
> В `TogoUITests/ОнбордингНиз` теперь оба: геометрия низа уехала
> на дешёвый вход и перестала зависеть от порядка тестов, а два теста,
> которые **считают собак**, остались на настоящем — под `-Онбординг`
> они мерили бы базу, в которую нарочно не пишут. Дешёвый вход
> **обходит** оба ворота, а не проходит их.
>
> И следствие, оплаченное 21.10: онбординг потребляет тест, идущий
> по алфавиту ПЕРВЫМ, а остальные получают главный экран. Стирание
> делает скрипт один раз на партию, не перед каждым тестом.

Второй воротник независим: `OnboardingFlow:20 isReplay = !dogs.isEmpty`.
Путь «пройти онбординг заново» подменяет шаги и кончает поток
на первом же подменённом (`onDone: finish`) — из шести шагов повторным
путём достижим один. Проверять онбординг «руками через настройки»
значит проверить один экран из шести.

`isHittable` отвечает про видимость, а не существование: для кнопки
верный вопрос, для текста — нет, и ответ «нет» читается как «в
приложении этого нет».

                                      16-…-НАЛОЖЕНИЕ.png`), четыре годных
```

Верное на 15.10 было: **условие стенда есть, а годного замера в нём
нет ни одного.** Верное на 28.10 другое: **годные кадры есть, а кадра
«после починки наложения» нет** — дефект на SE снят 25.10 и с тех пор
не переснимался, набор отстал на 371 коммит. Условие по-прежнему
отдельное от «узкий экран» и «крупный кегль», а их пересечения
не покрыто ни одним кадром.

> **Отрицательное утверждение «ни одного» никто не перепроверяет,
> потому что никто не ищет отсутствия отсутствия.** Три утверждения
> этого свода и `СТАТУС.md` оказались 15.10 ложными **в момент
> записи** — не устаревшими. Лечение другое: у «ни одного» обязан
> стоять замер **в той же строке**, иначе оно живёт, пока кто-нибудь
> случайно не наткнётся на противоположное. Эта строка прожила ложной
> двое суток и была дважды использована как основание.

> **И вторая её редакция тоже устарела — за тринадцать дней, молча.**
> «Три, и все три негодные» было верно 15.10 и неверно 28.10: кадров
> десять, годных четыре. Поправка, написанная как замер с датой,
> стареет так же, как утверждение без даты, — разница только в том,
> что её **можно** перепроверить. Поэтому замер здесь датирован
> дважды, и следующий читатель обязан отнестись к числу «десять»
> ровно так же.
