**«Togo ФИНАЛ.dc.html» — четыре разных документа.** Тот, что лежит
в каталоге с самым убедительным именем (`design_handoff_togo_final/`),

«`sha256` сверен дважды» верно про слепок как целое — и не отвечает
на вопрос, какой из четырёх документов имелся в виду.

> **Имя файла не называет документ.** Копию, по которой работают,
> называть хешем.

Для ответа про онбординг это оказалось безразлично, **и это проверено,
а не предположено**: раздел онбординга во всех четырёх копиях
идентичен — те же три метки, те же заголовки, те же поля. Для любого
другого раздела не проверено.

### Светлой и тёмной пары в слепке НЕТ

```

скрипт в <head>    читает ?theme=light|dark из URL и ставит data-theme
```

Тема здесь — **свойство просмотра**, тумблер документа, а не два
нарисованных ряда. В Figma ряды нарисованы (ряд 1 Dark, ряд 2 Light,
320 × 568).

> **Для задачи «светлая и тёмная версия онбординга» этот слепок
> источником быть не может по устройству:** он содержит не пару,
> а одну отрисовку с переключателем.

## Почему именно так

### Два задания Виктории спорят на одном шаге

```
                       контракт/HTML     Figma 1c          код
Запуск («Togo»)        есть (v2, :115)   01 Запуск         НЕТ
Приветствие, обещания  НЕТ               НЕТ               welcome ✓
Кличка и вес           Онбординг 1       02 Кличка         dog ✓
Кличка пустая          НЕТ               03 Кличка пустая  НЕТ
Фраза (как просится)   НЕТ               04–06 Фраза       НЕТ
Режим дня и питание    Онбординг 2       НЕТ               schedule ✓
Уход                   НЕТ               НЕТ               care ✓
Семья, приглашение     НЕТ (раздел 7)    12–15 Позвали     family ✓
«Сегодня» в потоке     НЕТ               07–09 Сегодня     НЕТ
Уведомления            Онбординг 3       10 Уведомления    notifications ✓
Системный запрос       есть (v2, :117)   11 Системный      внутри notifications
```

Слово «позвали/приглашение» во всём HTML встречается **один раз**:
ветки приглашения в онбординге там нет, контракт кладёт «Принять
приглашение» в раздел 7, а Figma делает из него четыре экрана потока.

**Конфликт, который разрешает только она:**

```
шаг «Режим» (Еда · Лекарства по часам · Туалет)
   контракт/HTML   ЕСТЬ, целый экран из трёх
   Figma 1c        НЕТ ни одного экрана
   код             ЕСТЬ, шаг .schedule
```

Перенести поток «по Figma целиком» значит удалить шаг, который контракт
пакета объявляет одним из трёх, — и вместе с ним единственное место,
где спрашивают режим питания. На нём, по доккомментарию
`OnboardingSteps:168-170`, стоит способность приложения подсказывать
время кормления и замечать переедание.

Плюс `care` и `family` не существуют **ни в одном** из двух макетов,
а в коде это шаги 3 и 4: перенос по Figma удаляет три шага из шести
и добавляет восемь новых.

> «Реализовать `Togo ФИНАЛ.dc.html`» и «перевести поток по макету
> Figma» — **два разных задания**, и на шаге «Режим» они
> противоречат друг другу. Слово нужно ДО первой строки, а не после:
> оба решения её, и ни одно не выводится из другого.

Правдой ни один из двух не объявляю. HTML — слепок от 07.10 15:12,
на сутки **старше** решения 08.10 «правда по макетам переезжает
в Figma».

## Что это меняет для человека с собакой

Пока ничего: ни строки не изменено. Но если поток перенесут по Figma,
не назвав судьбу шага «Режим», человек перестанет сообщать, сколько
раз в день ест его собака, — и приложение потеряет основание
для подсказок о кормлении и для замечания переедания. Молча: ни один
тест этого не ловит, потому что ловить надо отсутствие вопроса,
а не неверный ответ.

кроме онбординга, назвать копию **хешем**, а не именем. Четыре
