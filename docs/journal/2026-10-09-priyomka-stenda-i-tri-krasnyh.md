## Приёмочный лист: написан ДО результата и оплатился до результата

Четыре ловушки нашлись прогоном листа на настоящем логе (`build/unit.log`),
прежде чем лист стал листом. Ни одна не упала бы на синтетике.

```
ОБА маркера в одном логе     ** TEST FAILED ** и ** TEST SUCCEEDED **
                             стоят разом → зелень по присутствию строки
                             итога ложна ПО УСТРОЙСТВУ: целей несколько
нет «Test run with N tests»  ⇒ «сверять нечем», не зелень и не краснота
skipped = 1 при нуле         предупреждение сборщика про AppIntents
error: = 3 при нуле          считать форму файл:строка:столбец:
```

**Пункт 5½, дал менеджер, проверен мной в обе стороны:**

```
caught …Exception   12 при ** TEST FAILED ** = 0
на здоровых логах   0 — правило не перетянуло
```

Четыре (и двенадцать) пойманных исключения при нуле маркеров падения.
Шаблон держать **простым** (`caught`): `ugrep` падает на
`.{0,90}caught` с «exceeds complexity limits» — нарядный шаблон молча
не совпадёт, то есть ложный ноль у самого сторожа.

### Строка итога НЕДОСЧИТЫВАЕТ — и расхождение растёт

```
заход 2   имена ✔+✘ = 108  ↔  строка итога «103 tests»   (−5)
заход 3   имена ✔+✘ =  19  ↔  строка итога   «3 tests»   (−16)
```

Мы знали, что она **завышает доверие** словом `passed`. Занижение
счёта — новое, и оно внутри одного лога: строка расходится
с собственным поимённым выводом.

> **Выполненное против порога считать счётом имён `✔`+`✘`, а не
> строкой итога.** Иначе порог сверяется с величиной, которая сама
> себе противоречит.

## Лист асимметричен, и это свойство предмета

```
ЗЕЛЁНЫЙ при помехах   вывод надёжен: зелень при помехах — зелень тем более
КРАСНЫЙ при помехах   не надёжен ни в какую сторону
```

Поэтому красное принимаю как «не установлено», а не «вершина красная».
Объявить вершину красной по негодному прогону — значит назначить
следующей смене поиск дефекта, которого может не быть; ищущий найдёт.

## Улика умерла вместе с worktree

```
логов вечерних прогонов 08.10   НЕТ НИ ОДНОГО
шесть каталогов prunable        СТЁРТЫ вместе с логами
в build/*.log новейшее          17:19
выжил                           один .ips, и он про watchdog 0x8BADF00D
```

> **Мы ввели `/tmp`-worktree, чтобы у числа был адрес, — и получили,
> что у числа адрес есть, а у лога нет.** Правило «улика на этой машине
> — улика нигде» применяли к `/tmp` против репозитория, а не к worktree
> против вершины.

Отсюда: **логи прогона писать в `build/logs/` вершины** — форма взята
у `projects-53`, который её применил, а не выдумана. Применена
`projects-95` в тот же час: заходы 2 и 3 читались мной со стороны,
чего 08.10 не было ни у кого.

**И граница этой починки, которую надо назвать сразу:** `build/`
лежит в `.gitignore`. «Лежит в репозитории» ≠ «лежит в git». Форма
решает **одну** задачу — пережить worktree — и **не** решает
«пережить машину»; для второго улика обязана попасть в доклад текстом
или в коммит числом. Разделять это нарочно: прочтут как одно.
