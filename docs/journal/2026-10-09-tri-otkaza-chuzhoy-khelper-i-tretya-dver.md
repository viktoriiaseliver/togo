## Предмет: приложение подтверждало галочкой запись, которой не сделало

`EventLog` — единственная дверь, которой запись попадает в дневник;

краевой.**

в `DayPlanActions` («Снова в списке», «Доза отмечена пропущенной»,

## ЗДОРОВЫЙ ПРОГОН ПОКРАСНЕЛ ПЕРВЫМ — и нашёл дефект в ЧУЖОМ стороже

Главное этой половины, и это не моя правка. Первый здоровый прогон дал
`rc=65`: два новых утверждения покраснели **на починенном коде**.
Причина — хелпер `тело(функции:в:)` из `341c1ec`:

```
func record(… configure: (LogEvent) -> Void = { _ in })
прежний разбор брал ПЕРВУЮ { после имени — а это АРГУМЕНТ
«тело»              6 символов, « _ in »
showFailure в нём   0
после починки       2080 символов, showFailure 3
```

> **Красный здесь безобиден — он виден. Опасна обратная половина того
> же дефекта: любое утверждение «тело НЕ содержит X» на шестисимвольном
> теле проходит ВСЕГДА, то есть даёт ложную ЗЕЛЕНЬ.** Один дефект
> разбора, два исхода, и зелёный не видит никто. Мы знаем этот класс
> только с красной стороны именно потому, что красный виден.

Починено счётом круглых скобок до закрывающей скобки списка параметров:
вложенные `(…)` в типах (`(LogEvent) -> Void`) иначе обрывают поиск
на середине.

**Поведение чужого теста проверено, а не предположено.** Единственный
прежний зовущий — `исходПрочитан` в `FamilyShare.swift`; оба разбора
дают на нём один результат, 25 символов, то же содержимое. Правка
снимает дефект и не трогает работавшее.

### Причина «висения» измерена, и у неё есть имя команды

```

```

**`xcodebuild` после УПАВШЕГО теста собирает диагностику симулятора
с таймаутом 600 секунд.** Тесты кончаются за 0,3 с, строка итога уже
в логе, а процесс стоит ещё до десяти минут на нуле процессора.

```

гасить               ТОЛЬКО simctl diagnose, не xcodebuild:
                     гашение xcodebuild портит следующий прогон
                     и даёт ноль выполненных
```

Это снимает наше «третье состояние процесса: жив и висит» с загадки
на механизм — и снимает с именем команды. Трижды за эту половину

### Продуктовый вопрос, который я назвал, а не решил

У `showFailure` не было параметра действия — значит «просто позвать
его» означало бы **убрать кнопку «Отменить»**, а текст обещает её
словами «попробуй ещё раз». Убирать или оставлять — вопрос не
инженерный. Поэтому у `showFailure` появился необязательный `action`

что было неверно, — **знак**. Выбор между «оставить кнопку» и «убрать

## Поправка к своему же замеру: узкий шаблон молчит

Находка `projects-53`, проверена `projects-6e`, и она бьёт по числу,
которое я напечатал в `140bc86` как замер:

```
мой шаблон        grep -cE '^/.*: error:'
не ловит          <unknown>:0: error: error opening input file
                  — номер ОДИН, не два
я доложил         «ошибок вида файл:строка: error: 0»
```

> **Ноль по адресной форме при ненулевой `<unknown>` значит
> «инструмент не состоялся», а не «ошибок нет».** Обратная сторона
> `grep -c "error:"` → 1921 при нуле настоящих: там шаблон слишком
> широк, здесь слишком узок, **и узкий опаснее — он молчит.**

**Вывод «предикат собрался в обоих таргетах» остаётся верным, но стоит
он не на этом числе, а на артефакте:** `.xctestrun` был на месте,
и приёмку сборки я брал им. Артефакт есть либо нет, и «есть» не бывает
по ошибке.

> **Два признака разной надёжности стояли рядом — и слабый оказался
> тем, который я напечатал.**

Проверить то число на своём логе уже нечем: лог уехал вместе с worktree
при уборке. **Это названо, а не умолчано.** Скрипт приёмки третьей
двери печатает теперь три числа рядом — адресных, `<unknown>`, всех
вхождений — и при `<unknown> > 0` говорит «отказ инструмента», а не
«ошибок нет».
